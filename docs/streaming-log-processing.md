# การรับและตรวจ log ของ SIEM KKU

อัปเดต 14 ตุลาคม 2026 ส่วนนี้เปลี่ยนระบบรับ log, การตรวจจับ และข้อความช่วยเหลือ
โดยคง UI ของ Wallboard และค่า credentials / TLS เดิมไว้

## ลำดับการทำงาน

1. รับ POST `/api/ingest` หรือดึง GET ผ่าน Settings → Log API
2. บันทึกต้นฉบับลง PostgreSQL ก่อนตอบรับ `201` การตอบรับยังไม่ใช่การตรวจเสร็จ
3. worker อ่านงานต่อเนื่อง ครั้งละไม่เกิน 250 รายการและงบข้อมูล 2 MiB
4. engine แปลงรูปแบบ log แล้วตรวจ rule และ heuristic ทุกชุด
5. เก็บผลตรวจในฐานข้อมูลก่อนสร้าง incident เมื่อ incident rollback จะใช้ผลเดิม
   แทนการส่ง log เดิมไปนับในหน้าต่างพฤติกรรมซ้ำ
6. บันทึก incident และผลประมวลผลใน transaction เดียว จากนั้นจึงส่ง WebSocket
   และเข้าคิว Slack ตามนโยบาย การส่งข้อความไม่ใช่เงื่อนไขในการบันทึกหลักฐาน

คิวอยู่ในฐานข้อมูล มี lease สำหรับกู้งานหลัง worker หยุด และใช้ `SKIP LOCKED`
พร้อม partial index สำหรับงาน pending / lease ที่หมดอายุ จำนวน receipt ไม่ถูก
โหลดทั้งหมดเข้า RAM เมื่อต้นทางได้รับ `503` ให้รอแล้วส่งซ้ำด้วย ID และข้อมูลเดิม

## หน้าเว็บที่ใช้ตรวจปัญหา

| หน้า | ใช้ดูอะไร |
| --- | --- |
| Settings → Log API | URL, รูปแบบ JSON, API key, asset และ cursor ของต้นทาง |
| Log Ingestion | รับจริงหรือไม่, pending / processing / processed / failed / quarantined, อายุคิว และสถานะโมเดล |
| ผลตรวจจับ | ผลทุกระดับ รวมรายการที่ยังไม่เข้าเกณฑ์ alert หรือไม่ทราบ IP เป้าหมาย |
| Dashboard และหน้าเดิม | incident ที่มีหลักฐานเข้าเกณฑ์และเกี่ยวข้องกับ LAN ที่ลงทะเบียน |
| Integrations → Slack Alert Policy | กฎ, cooldown, เพดานส่ง, คิว และพรีวิวเหตุผลโดยไม่ส่งจริง |

ปุ่ม `?` แสดงคำอธิบายเมื่อ hover, focus ด้วยคีย์บอร์ด หรือแตะบนมือถือ
กด Escape หรือแตะนอกกรอบเพื่อปิด

### เหตุใดรับ log แล้วอาจไม่เห็นบน Dashboard

- `benign`: ไม่พบรูปแบบโจมตี ไม่สร้าง incident เพียงเพราะมี HTTP request
- `blocked_traffic`: ถูกปฏิเสธอย่างเดียว ยังไม่ใช่หลักฐานว่าโจมตีสำเร็จ
- `suspicious`: มีผลตรวจ แต่หลักฐานหรือคะแนนยังไม่เข้าเกณฑ์ alert
- ไม่ทราบ target: ยังเก็บผลที่หน้าผลตรวจจับ ตรวจ `server_addr` / `dstip`
  หรือกำหนด IP ของเครื่อง web ที่ถูกเฝ้าระวังใน Log API อย่าใช้ IP ของ SIEM
  แทนเป้าหมายเพื่อให้ผ่านกฎ LAN ระบบติดป้ายเมื่อใช้ asset สำรองจากการตั้งค่า
- timestamp เก่า: เวลาเกิดเหตุยึดจาก log ให้เลือกวันที่ย้อนหลังบน Dashboard
- `failed` / `quarantined`: เปิดดูเหตุผลและรูปแบบ log ก่อนลองใหม่

การตรวจ LAN ใช้เครือข่ายที่ลงทะเบียน พิจารณาทั้งขาเข้า ขาออก และภายใน
ขาออกระบุหน่วยงานของต้นทางใน LAN รายงานใช้ขอบเขตเดียวกัน ส่วนผลที่ไม่ทราบ
ขอบเขตยังอยู่ในหน้าผลตรวจจับและต้นฉบับ ไม่ถูกทิ้งเงียบ ๆ

## ดึงอัตโนมัติและข้อมูลซ้ำ

`Test GET` อ่านตัวอย่าง ไม่บันทึก log และไม่เลื่อน cursor ปุ่มดึง log และการดึง
อัตโนมัติใช้ค่าที่บันทึกแล้ว หน้าจอแยกจำนวนอ่านได้ บันทึกใหม่ และข้อมูลซ้ำ

API ต้นทางต้องรองรับ cursor จึงจะดึงต่อได้ ตั้งชื่อ query parameter และตำแหน่ง
next cursor ตามรูปแบบจริง แต่ละหน้าจะเลื่อน cursor หลัง ACK ลงฐานข้อมูลสำเร็จ
หากล่มกลางหน้า รายการที่บันทึกแล้วคงอยู่และส่งซ้ำได้โดยไม่สร้างรายการใหม่

ค่าเริ่มต้นรับไม่เกิน 1,000 รายการ / 2 MiB ต่อหน้า, สูงสุด 10 หน้าต่อรอบ
ตั้งได้ไม่เกิน 20 หน้า รอบดึงหยุดระหว่างหน้าเมื่อใช้เวลาประมาณ 20 วินาที
หากต้นทางคืนเฉพาะรายการล่าสุดโดยไม่มี cursor ระบบไม่สามารถกู้รายการที่
ต้นทางเลิกส่งได้ ควรใช้ cursor หรือ POST แบบ batch สำหรับข้อมูลจำนวนมาก

การดึง API ป้องกันข้อมูลซ้ำจากเนื้อหา raw log จึงควรคง timestamp หรือ ID
ต้นทางไว้ในข้อมูลจริง สำหรับ POST ให้ใช้ `event_id` ที่ไม่ซ้ำต่อเหตุการณ์
และใช้ ID เดิมเมื่อ retry

## ตรวจย้อนหลัง

ผู้ดูแลลองตรวจ failed ใหม่หรือสั่งตรวจ processed ที่ยังมีต้นฉบับได้ รายการที่
เคยตรวจแล้วใช้โหมด backfill ไม่ส่ง Slack และไม่รวมกับหน้าต่าง live ของ scan
failed ที่รับมานานเกิน 5 นาทีจะใช้ backfill เมื่อผู้ดูแลสั่งลองใหม่เช่นกัน

นำเข้าข้อมูลย้อนหลังผ่าน POST ให้ระบุ `processing_mode: "backfill"` ใน envelope
ระดับเดียวกับ `source` กฎ signature และรูปแบบข้อความยังทำงาน การตรวจย้อนหลัง
จากรายการเดี่ยวไม่ยืนยันการ scan หลายเหตุการณ์ และไม่ลบ incident เดิมเพียง
เพราะกฎจากรายการเดี่ยวไม่พบผล จำนวน hit และข้อมูลจัดการ case เดิมคงอยู่

ต้นฉบับของข้อมูลปกติหมดอายุหลังประมวลผลสำเร็จ 24 ชั่วโมงตามนโยบายเดิม
receipt ID, digest และ metadata ยังคงอยู่ ปุ่มตรวจซ้ำจะไม่เปิดสำหรับต้นฉบับ
ที่หมดอายุแล้ว ข้อมูลโจมตีและหลักฐานที่สัมพันธ์กับ incident ไม่ใช้การล้างนี้

## Slack และ AI

ค่าเริ่มต้น High ต้องมีหลักฐานและคะแนนอย่างน้อย 80, รวมกลุ่ม 60 วินาที,
cooldown 600 วินาที และส่งสูงสุด 5 ข้อความต่อนาที Critical ที่มีหลักฐานและ
คะแนนอย่างน้อย 85 เข้าคิวทันที แต่ยังผ่านเพดานรวม Port Scan ที่มีหลักฐาน
rule ใช้เกณฑ์เดียวกับการโจมตีอื่น การทดสอบ webhook สำเร็จไม่ได้แปลว่าทุก log
จะถูกส่งเป็นข้อความ

ยังไม่มีชุดข้อมูลติดป้ายกำกับหรือโมเดลที่ฝึกจริง ตัวตรวจปัจจุบันใช้ rule,
heuristic และ regex คะแนนเป็นน้ำหนักความเสี่ยง ไม่ใช่ความน่าจะเป็นที่สอบเทียบ
หรือหลักฐานว่าระบบถูกเจาะสำเร็จ AI KKU ช่วยสืบค้น/อธิบาย incident ตามคำขอ
ของผู้ใช้ ไม่ส่ง log ทุกบรรทัดไป LLM

รองรับ ONNX shadow เมื่อมีโมเดลที่ผ่านการประเมินแล้ว ค่าเริ่มต้นไม่ติดตั้ง
runtime หรือโมเดล ดู `detection-engine/models/README.md` Shadow ใช้ sampling
และไม่มีอำนาจเปลี่ยน alert / Slack จนกว่าจะมีหลักฐานจากข้อมูลที่ติดป้ายจริง

## ผลทดสอบและขอบเขตหลักฐาน

ทดสอบในเครื่องกับ PostgreSQL 16 และ engine จริง โดยใช้ log fixture แยกจาก
ข้อมูลมหาวิทยาลัย ไม่มีการส่ง Slack จริงหรือเรียก AI KKU จริงในการทดสอบโหลด

การ soak รอบแรกสะสม 643,500 รายการและพบคอขวด query ที่สแกน processed receipt
แก้ด้วย partial index และแยก pending ออกจาก lease recovery หลังแก้ ทดสอบบน
ฐานข้อมูลเดิมที่มีมากกว่า 640,000 รายการแล้ว:

| รายการ | ผล |
| --- | --- |
| 10,000 log/นาที 10 นาที | 100,000 รายการ |
| 30,000 log/นาที 2 นาที | 60,000 รายการ |
| ACK และประมวลผล | ครบ 160,000 ไม่มีงานค้าง |
| ผลบวกที่กำหนดใน fixture | พบครบ 320 รายการ |
| เวลารับจนตรวจเสร็จ p95 | 932 ms |
| เวลาสูงสุดในชุดนี้ | 2,294 ms |
| RAM ที่สุ่มวัดสูงสุดทุกนาที | backend ประมาณ 247 MiB / engine 51 MiB |
| ตัวนับคิวเทียบ receipt จริง | ตรงกัน |

engine regression 37 ข้อ, PostgreSQL rollback / dedup / lease / retention,
การดึง HTTP จริงกับ cursor, production build และ UI ผ่าน HTTPS Nginx ผ่าน
ตรวจหน้าจอ 1600 / 768 / 390 px และ tooltip ด้วยคีย์บอร์ด/การแตะ

ผลนี้เป็นการตรวจความถูกต้องของ pipeline กับ fixture และความสามารถในเครื่อง
ทดสอบ ไม่ใช่ค่า precision/recall จาก log จริง และยังไม่ใช่ soak 24 ชั่วโมง
บน UAT ต้องวัดซ้ำกับแหล่งข้อมูลและทรัพยากร server จริงหลังอัปเดต

## อัปเดต server

ไฟล์ส่งขึ้น server ใช้ `deploy.tar.gz` ชุดเดียว รวม `.env` และ TLS เดิม
ไม่รวม node_modules, build output, log ทดสอบ, ฐานข้อมูล, `.release` หรือ `.trash`
ไม่มี release installer และไม่มีขั้นตอน checksum เพิ่มเติม

จากโฟลเดอร์งานหลักบน Windows:

```powershell
.\deploy.ps1 -ServerIP 10.101.104.234 -Username napat -RemoteDir '~/siem_v2'
```

หรือเมื่อวาง archive ใน `~/siem_v2` บน server แล้ว:

```bash
cd ~/siem_v2
sudo tar -xzf deploy.tar.gz scripts/deploy-server.sh
sudo bash scripts/deploy-server.sh
sudo docker compose ps
sudo docker compose logs --tail=60 backend detection-engine nginx
```

script แทนที่ source, build และรัน migration ก่อน backend เริ่มทำงาน
คง database volume / uploads และสร้าง Nginx ใหม่เพื่อให้ใช้ upstream ปัจจุบัน
ไม่มีการเชื่อม SSH หรือ deploy UAT อัตโนมัติจากการทดสอบในเครื่องครั้งนี้
